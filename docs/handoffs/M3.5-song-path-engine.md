# M3.5 E1: Song Path engine and finite queue

**Status: DONE (engine + playback; no UI yet).** Clean start at 2ceb4f41. E split: E1 engine (this),
E2 Discover card + song/mood picker (next).

## Implemented

- `data/audiomuse/SongPath.kt`: `SongPathBuilder.build(sourceId, start, end, length)` with
  `AudioMusePathEnd` ends (song ID or one of the five path moods). `canBuild`: both ends set, at most one
  mood, not the same song, no blank IDs (iOS `SongPathService.canBuild`). Length clamped to 5–50, default
  25 (iOS). `findPath` → C3 resolver → local songs in AudioMuse order, **each once** (iOS de-duplicates;
  the earlier reference note said "preserve duplicates", iOS behaviour wins). Results: Ready, InvalidEnds
  (no client created), NoPath (404, empty path, or nothing local), Unavailable (offline, other source, no
  or unreadable config). Other errors propagate for a "couldn't build" message.
- `data/audiomuse/AudioMuseRequests.kt`: `guardedAudioMuseRequest`, the gate + watcher shared by mood radios
  and Song Path (source/offline/config change cancels). `MoodRadioBuilder` now uses it (behaviour unchanged;
  its tests pass).
- `playback/SongPathPlayer.kt`: builds for the active source, rechecks it, plays via `playMix` as
  `QueueCollection.SongPath` ("Song Path").
- `QueueCollection.finite`; `PlaybackController.finiteQueue` (from the stored source label, also after
  restore) makes `refillActive` false: neither autoplay similar nor a built-queue refill extends a path.
- Koin singletons `SongPathBuilder`, `SongPathPlayer`; AppModuleTest resolves them and MoodRadioPlayer.

## Decisions

- No Room cache for path results and no offline fallback: like mood radios, the action needs AudioMuse and
  E2 will hide the card offline. Recorded with the other AudioMuse decisions (issue #16).
- Queue heading is plain "Song Path"; iOS shows "Song Path · From → To". A dynamic label needs a
  label format the controller can still recognise as finite; left for E2 or later.
