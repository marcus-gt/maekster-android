# M2.11 Part C: restore edge cases and process death

**Status:** DONE. M2.11 is complete. Based on 7701cc80 (Parts A and B: `M2.11-swipe-away.md`,
`M2.11-quality-presets.md`).

## Problem

The cursor stored a queue position and a time, but not which song the time belonged to. Album,
playlist and artist entries resolve their songs from the library on restore. If a sync deleted the
playing song, or added one before it, the saved position pointed at a different song, and it resumed
at the old song's time (for example 3:10 into the next track).

## Implementation

- Schema 54 (`MIGRATION_53_54`): adds the nullable `playback_cursor.positionSongId` column. Rows written
  before the migration keep null, which means "unknown", so the old behaviour applies.
- `QueueRepository.setPosition(positionMs, songId = null)` stores the song with the time.
  `positionSongId()` reads it. `setCursor` to a different position clears both, as it already
  cleared the time.
- `PlaybackController`: every position save (ticker, pause, seek) passes `player.currentItem?.id`.
  `restore()` then:
  - If the song at the cursor is the saved song, behaviour is unchanged.
  - Otherwise `restoredSongPosition` looks for the saved song in one bounded window
    (`QUEUE_WINDOW_RADIUS`, nearest to the cursor, no materialization). If found, the cursor and time
    move there (a track was inserted before it, or the queue was reordered).
  - If it isn't there, the song was deleted: the track now at the cursor (the next one) loads from
    0:00 and the saved time is cleared. Logged as `playback: restore: saved song … is gone`.
- Changed source was already handled: restoring a queue from a server other than the active one stops
  it (`restoringAQueueFromAnotherSourceStopsIt`). That's unchanged.

## Known issues and notes

- A stale incremental Kotlin build reported false "Unresolved reference" errors (`ARTIST_ART_UPDATE_SQL`,
  `toQueueItem`). `./gradlew :app:compileDebugKotlin --rerun -Pkotlin.incremental=false` fixed it.
  The IDE's own build at that time installed an APK that crashed with a ClassNotFoundException
  for `SettingsViewModel`; that's the same cause, not a code bug.
- Emulator oddity, not investigated: `adb shell input keyevent KEYCODE_MEDIA_PAUSE` did not pause our
  session. About 5 s later the queue was replaced by the album "Shape The Future" ("Broken Jazz",
  `transition=playlist`). There is no `onPlaybackResumption` in the app, so the trigger is unknown.
  This may be worth a look: a hardware media key should never replace the user's queue. Use the
  in-app button for pause in emulator tests.
- Positions save every 15 s while playing, and on pause and seek. A process death mid-play can lose
  up to 15 s, by design.
