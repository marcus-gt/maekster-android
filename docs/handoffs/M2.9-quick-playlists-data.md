# M2.9: quick playlists, data layer and quick add

**Status:** DONE for the data layer; the long-press menu, picker and Settings screen remain.
Based on de9d7554.

## iOS behaviour (QuickPlaylists.swift, QuickPlaylistMenu.swift, QuickPlaylistsTests)

Per-server ordered list; toggle appends or removes; move/delete in Settings; renames followed and
deleted playlists dropped; "Also like the song" on by default. Quick add re-reads the playlist,
shows "Already in …" without adding, otherwise appends, records Recent and confirms; then, if the
preference is on and the song is not liked, likes it. A failure shows an error and likes nothing.

## Implementation

- Schema 52 (`MIGRATION_51_52`, `52.json`): `quick_playlists (sourceId → sources cascade,
  playlistId, position)`, PK (sourceId, playlistId). Room rather than DataStore because, like pins,
  it is relational per-server data joined with the mirror.
- `QuickPlaylistDao`: `resolved` (JOIN playlists, in position order, so names follow the mirror and
  playlists no longer mirrored are hidden but kept, like Recent), `contains`, `add` (appended at
  MAX+1, ignore duplicates), `remove`, transactional `replace` for reordering.
- `QuickPlaylistRepository` (Koin single): `quickPlaylists`, `toggle`, `remove`, `move(from,to)` on
  the visible list (rewriting drops hidden rows), and `add(sourceId, playlistId, songId)`. That reuses
  `PlaylistRepository.add(… Duplicates.Skip)` (fresh read, append only if missing, mirror, Recent),
  returns `Added` / `AlreadyThere`, then favorites via `LibraryRepository.setStar` (offline outbox
  and rollback included) if the preference is on and the mirror says the song isn't starred.
  Failures propagate (Offline/NotFound/network) and favorite nothing.
- `UserPreferences.quickPlaylistsAlsoFavorite()` (DataStore, default true) and its setter.
  Android uses "Favorites" wording where iOS says "like".
- Recent is recorded even when the song was already there (iOS records only real additions).
  It's harmless, so I left it as is.
