# M2.10 Part B: Transfers on the Downloads screen

**Status:** DONE in code and JVM tests; emulator check pending (a real download is needed to see the
states). Based on abfd13bd (Part A: `M2.10-download-ownership.md`).

## iOS (DownloadedView + DownloadActivitySection)

A "Transfers" section first: each song not yet on the device with its state (Queued, Waiting for
connection…, Downloading… with progress and bytes, Finishing download…, Download failed with the
reason), Retry for failures and Cancel for every row. Then Songs / Albums / Playlists sections of
downloaded content, sortable by name or recently downloaded.

## Implementation

- `DownloadedSong` now carries `error` (`d.error` in `DownloadDao.downloadedSongs`).
- `DownloadsViewModel.transfers`: every non-completed song, running first, then queued, then failed
  (`transfersOf`). `retry(song)` → `DownloadRepository.download` (restarts a failed download);
  `cancelTransfer(song)` → `cancel` for active rows, `remove` for failed ones.
- `DownloadsScreen`: when there are transfers, a "Transfers" header and one `TransferRow` per song,
  above the summary and tree. Each row shows the title, a status line (Downloading / Queued / the
  `DownloadError` message, or Failed), and, while running, a determinate or indeterminate bar plus
  "X of Y". It has Retry (failed only) and Cancel icon buttons labelled with the song title.
- Not mirrored: "Waiting for connection" (Android hands transfers to DownloadManager, which waits for
  the allowed network itself; the app doesn't currently see that reason) and "Finishing download"
  (no post-processing/remux on Android). Grouping stays the existing artist → album tree. iOS's
  Albums/Playlists sections and name/recent sort are a possible follow-up, but the tree already
  covers browse and delete.
