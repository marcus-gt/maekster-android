# M2.9: reorder retry

**Status:** COMPLETE for process-local matching reorder retries; committed with this handoff.
Based on 9a956ae4.

## Implementation

- PlaylistRepository retains an immutable original/desired order per source + playlist before
  replacement. A mutex serializes reorder intent access and replacement/readback.
- A retry must supply the identical original and desired lists. It accepts the original server
  order or an exact ordered prefix of the desired list (the state left by batched replacement).
  A full desired order means a lost response: read back without another write.
- Partial retries restart the existing idempotent replacement; duplicates keep their exact
  occurrence counts/order. The mirror stays at the original order until successful readback.
- Intent clears after successful readback or a conflict. Conflicts still refresh the mirror and
  report Changed, without another write. A prefix without retained intent is a conflict.
- Existing moveEntry callers benefit by repeating the same menu move while the mirror is unchanged.
  No UI, schema, dependency or playback change.

## Limits / remaining

- Intent is process-local. After restart, or if sync changes the mirror between attempts, the old
  menu move is not a retained draft; server/mirror recovery UI remains future work.
- Subsonic has no conditional versioned playlist write. An external change producing exactly the
  same prefix is indistinguishable from our partial result; reads/writes also retain the existing
  race between clients. Non-prefix conflicts are protected.
- Restarting a partial replacement resends all desired batches; it does not append only the tail.
