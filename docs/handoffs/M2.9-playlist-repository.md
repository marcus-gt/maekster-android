# M2.9 Part B: playlist repository and mirror refresh

**Status:** COMPLETE. Based on 365d9d18; committed with this handoff.

## Implementation

- `PlaylistRepository` (data/repo): each edit goes to the server, then the playlist is read back and
  mirrored with `LibraryDao.replacePlaylist` (one transaction: summary row plus `playlist_songs`), so
  lists, search, Home and queues see the server's result. No schema change.
- `PlaylistAddition` keeps its `PlaylistAppendIntent` across retries (baseline from a fresh server
  read, not the possibly stale mirror). `PlaylistCreation` keeps the created id, so a retry finishes
  the same playlist (iOS behaviour) and never creates a second.
- remove/reorder take the order the user saw (`shownSongIds`). If the server's order differs, nothing
  is written, the mirror is refreshed and `Changed` is reported, so the wrong song is never removed.
- Delete is idempotent (writer) and removes the mirror rows (`LibraryDao.removePlaylist`).
- `PlaylistEditException` reasons: Offline (no writer: offline mode / needs sign-in), NotFound
  (also drops the mirror rows), Changed, NotReported (server created but didn't say which).
  Server/network errors propagate as their own exceptions.
- `SourceRepository.playlistWriter(sourceId)`; Koin singleton `PlaylistRepository`.

## Known limits

- Network loss mid-edit surfaces as an IOException; the UI should offer Retry with the same object.
