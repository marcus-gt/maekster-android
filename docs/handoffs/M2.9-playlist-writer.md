# M2.9 Part A: playlist write foundation

**Status:** COMPLETE. Based on f06c7141; committed with this handoff.

## Implementation

- `SubsonicClient` takes ordered repeated query parameters (`repeated`) for `uri`, `check`, `stream`.
- `PlaylistWriter` (data/source) with `PlaylistDetail(playlist, songs)`: create (empty; songs go
  through append so a retry can tell what arrived), rename, setComment, append, remove (0-based
  positions), replace (ordered, used for reorder), delete, playlist (fresh read).
- `SubsonicPlaylistWriter`: createPlaylist / updatePlaylist (`songIdToAdd`, `songIndexToRemove`,
  `name`, `comment`) / createPlaylist with `playlistId` for replace / deletePlaylist / getPlaylist.
  Song lists go in batches of 100 (URL length behind proxies); a failed batch stops the edit.
  Removal sends highest positions first so later batches stay valid. Replace rewrites with the first
  batch, then appends the rest. Not found (code 70 or HTTP 404) makes delete succeed and a read null.
  An older server that answers createPlaylist with no body gives null.
- `SubsonicXml.playlistDetail` parses the playlist element and its entries in order, keeping
  duplicates and skipping blank ids (like sync).
- `PlaylistAppendIntent` (data/playlist): port of iOS's retry-safe append. It counts songs against the
  pre-append baseline, so a lost response isn't repeated, a partial append resends only missing
  occurrences in order, and existing duplicates or other people's additions are left alone.
