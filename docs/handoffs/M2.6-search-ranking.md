# M2.6 Part A: Search ranking

**Status:** complete (12 Nov 2026). M2.6 continues with scope chips and a top result (Part B), then recent searches
per server (Part C).

## Implemented
- Search results for albums, artists, playlists and songs are ranked by their title, as iOS's
  `LibrarySearchRanking.score` does: exact title, then title prefix, then title contains, then a match only in another
  indexed field (album artist, song artist, sort names). The existing name order breaks ties.
- The rank is in SQL (`*_SEARCH_RANK` in LibraryDao.kt), ahead of `LIMIT`, so an exact title is never cut off by the
  50-result cap (before, results were alphabetical and then capped).
- Matching is unchanged: the FTS5 trigram phrase match, 3-character minimum, source-scoped. No schema, dependency,
  network or UI change; the Search screen shows the same sections, now in rank order.

## Differences from iOS (documented)
- SQLite `lower()` folds ASCII only, so the rank compares other scripts case-sensitively, and diacritics are not folded
  ("joga" still finds "Jóga" only if the trigram match does; it does not today). iOS folds case and diacritics and
  strips punctuation. Folding in SQL would need a normalised title column (a migration); left for later if needed.
- iOS's token rule (every query word prefixes a title word) is not a separate rank: an FTS phrase match is contiguous,
  so such a title already ranks as contains or falls to "other fields".
- Cross-type ordering (an exact song above an artist prefix) arrives with the top result in Part B.
