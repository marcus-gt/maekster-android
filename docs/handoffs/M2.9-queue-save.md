## Implementation

- Schema 51 (`MIGRATION_50_51`, `51.json`): `playlist_save_drafts` (id, sourceId → sources cascade,
  name, size, created playlistId) and `playlist_save_draft_songs` (draftId → draft cascade, position,
  songId). `PlaylistSaveDraftDao` reads songs by position range and completes a draft in one
  transaction: upsert summary, replace `playlist_songs` via INSERT…SELECT from the draft, drop draft.
- `PlaylistRepository.stageSave(sourceId, name, Flow<List<String>>)` captures the export
  (`QueueRepository.playlistBatches`) into the draft, locally and before any network. A capture failure,
  empty capture or blank name leaves no draft. One draft per server: staging replaces the previous one.
- `saveDraft(draftId)`: create (playlistId persisted immediately, empty playlist mirrored), append
  draft batches of ≤100, read back with `PlaylistWriter.playlistBatches` and compare batch-by-batch
  with the draft, then complete the mirror from the draft, call `libraryChanged`, record Recent.
- Retry (same draft, even a new repository/process): reads the created playlist back, appends only
  what is missing (lost responses are not resent, no second playlist). Edited elsewhere → `Changed`
  with no write and no mirror refresh (left for sync; a bounded refresh would need staged readback).
  Deleted elsewhere → `NotFound`, playlistId cleared so the next run creates a new one. Readback short
  of the draft → IOException (retryable). `discardSave` drops the draft; a created playlist stays.
- Why staging: the queue export is invalidated by queue/library changes (including playback consuming
  up-next and our own mirror writes); the staged draft decouples the network save from that.
- Memory: ≤100 IDs per append/compare; never the whole queue or playlist. Saves are serialised by a
  repository mutex. No UI, DI, dependency or string change.
