# M2.7 Part I: Delayed playback waiting states

**Status:** complete (12 Nov 2026). Started in session maekster-android-6a, which stopped before verification;
finished in another session at the user's request. Based on clean 5fa57e41.

## Implemented
- `PlaybackState.waiting: PlaybackWaiting?` (Preparing, Buffering, Reconnecting) when playback should be running
  (play intent and a current item) but is not:
  - Reconnecting: a network retry (Part H) is armed for the same source, position and song.
  - Preparing: buffering at position 0 (a track or queue starting).
  - Buffering: buffering anywhere else.
- `PlaybackWaitingIndicator` hides waits shorter than 700 ms (`PLAYBACK_WAITING_DELAY_MS`, iOS
  `PlayerState.waitingMessageDelay` and `PlaybackContinuity.md`). A wait for one source and queue position is one
  episode: the reason can change within it without restarting the delay, and an already visible status updates at
  once. A new track restarts the delay; readiness, pause or stop clear it immediately; stop resets it.
- Now Playing shows the status under the format line (polite live region). The play control shows a spinner during
  a visible wait, also while Reconnecting with the player idle; its description stays "Pause" (tapping it pauses)
  with the status as state description. The mini player follows the same rule.
- Replaces the old 1 s `bufferingJob`/`showBuffering`; `isBuffering` now means a visible buffering wait. The stall
  watchdog is unchanged.
- Reconnecting appears only for an actual recovery attempt, not a watchdog, as iOS requires. No schema or
  dependency change. Strings: Preparing, Buffering, Reconnecting.
