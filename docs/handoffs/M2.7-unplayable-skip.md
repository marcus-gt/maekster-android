# M2.7 Part J: Bounded skipping of unplayable items

**Status:** complete (12 Nov 2026). Based on clean 64a37a66.

## Implemented
- `PlayerHandle.Listener.onError` now carries a typed `PlaybackFailure` (Network, Unplayable, Other).
  `playbackFailure(PlaybackException)` in Media3PlayerHandle classifies:
  - Unplayable: HTTP 404 or 410 on the stream, a missing local file, a malformed or unsupported container, and
    decoder init, decoding and unsupported-format errors.
  - Network: connection failed or timed out (Part H's retry still keys on the network message).
  - Other: everything else, including HTTP 401, 403 and 5xx, which would fail every item alike.
- On an Unplayable failure while playback is wanted, the controller moves on with the normal `next()` rules (Up
  next, offline downloads, repeat), and Media3's kept play intent resumes playback. This follows the iOS rule that
  "an unavailable queue advances through a bounded number of songs and stops safely when none are playable".
- The bound: at most 5 skips in a row (`MAX_UNPLAYABLE_SKIPS`). The 6th consecutive failure pauses with
  "Playback stopped: several tracks in a row couldn't be played." Android queues can be huge (references), so a
  fixed bound replaces iOS's per-song unavailable set. A run ends when a track actually plays (playing, not idle or
  buffering) or on user Play/Pause, Next, Previous or a new queue.
- Messages: one "Couldn't play “Title”, so it was skipped." per run, so snackbars do not pile up. The message
  never says the song was deleted: iOS claims that only after a structured not-found from the server, and Android
  makes no server request here. At the end of the queue, or with playback paused, nothing is skipped and the
  original error shows, as before.
- No schema, dependency or network change.
