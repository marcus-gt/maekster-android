# M3.1 Part C: ListenBrainz account, listens and offline queue

**Status:** DONE (no UI yet; Part D adds Settings). Based on 68bf02e4 (Parts A, B:
`M3.1-play-events.md`, `M3.1-listenbrainz-client.md`).

## iOS reference (ListenBrainzService)

- The token is validated, then stored securely with the username and server URL. A separate enabled
  switch exists, independent of server scrobbling.
- `playing_now` when a track starts. A `single` listen at the scrobble threshold; on success the
  offline queue is flushed with `import`.
- A transient failure (network, 429, 5xx) queues the listen; a permanent one drops it.
- Queued listens belong to one account. Changing the account or clearing the credentials empties
  the queue.

## Implementation

- `UserPreferences.listenBrainz()` returns `ListenBrainzSettings` (token ciphertext, root, username,
  enabled). Setters: `setListenBrainzAccount` (also enables), `setListenBrainzEnabled`, and
  `clearListenBrainzAccount` (keeps the root). The token is sealed with `CredentialStore`, like server
  passwords.
- `PendingListen` / `pending_listens` (schema 56, `MIGRATION_55_56`). It is global, not per server,
  because the ListenBrainz account is global. `PendingListenDao`: insert, oldest(limit), delete, clear,
  count flow.
- `ListenBrainzRepository` (`data/listenbrainz`) implements the new `playback.ListenSink`:
  - `state` (`ListenBrainzState`): connected, username, root, enabled, tokenUnreadable, pending.
    `active` = connected, enabled and readable.
  - `connect(token, root)` validates. Invalid → `InvalidToken`; network or HTTP failure → `Failed`,
    with nothing stored. A different token or root clears the queue. Then it stores, enables, flushes.
  - `disconnect()` clears the account and the queue; `setEnabled(true)` flushes.
  - `nowPlaying` / `listen` send only when active and the song can be named (`Song.toListenTrack()`
    needs a title and an artist).
  - `flush()` runs under a mutex, oldest first, in batches of 1,000. A transient failure, or 401,
    keeps the queue; another permanent rejection drops that batch so it can't block the queue forever.
- `Scrobbler` takes `listens: ListenSink?`. The play policy runs while either server scrobbling or the
  listen sink is active. Each event goes only to enabled targets, and the local play event (Part A) is
  recorded whenever a submission fires.
- Koin: `ListenBrainzRepository` with `OkHttpListenBrainzApi`, plus a song lookup on the active server.
  It flushes once at app start. Nothing is sent until the user connects an account (Part D).

## Verification

- `ListenBrainzRepositoryTest` (10):
  - connect: valid/sealed, invalid, failed;
  - nothing sent while signed out or disabled;
  - transient failure queued then imported after the next success; permanent failure dropped;
  - 1,001 listens imported as 1,000 + 1; a failed flush kept, then retried;
  - a Keystore reset gives an unreadable token and stops listens;
  - a different account or disconnect clears the queue; a song without a name is not sent.
- `ScrobblerTest` (+2): listens reach the sink while server scrobbling is off (server untouched, play
  recorded), and an inactive sink hears nothing. `MigrationsTest` (+1) covers 55→56.
- Mutations: queuing permanent failures fails the drop test; scrobbling to the server when only
  ListenBrainz is on fails the fan-out test. Both restored.
- No requests to the real ListenBrainz; there's no UI to connect from yet.
- Emulator (API 37): the deploy migrated the real database 54 → 56 (`play_events` and
  `pending_listens` present, empty) and the app started with no crashes, so the Koin wiring resolves.
- Checks: the full suite ran 1622 tests; only the three known HomeScreenshotTest timeouts failed, and
  that class passes 5/5 on its own. ktlintFormat reflowed one test; after that, ktlintCheck, lintDebug
  and assembleDebug pass.
